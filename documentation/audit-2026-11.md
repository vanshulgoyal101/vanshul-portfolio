# November 2026 engineering and discoverability audit

## Scope and evidence

This pass reviews the portfolio's React routes, content loading, article
navigation, SEO generators, service boundaries, SQL schemas, test infrastructure
and deployment checks. It builds on the existing architecture and feature
documentation rather than replacing working features with speculative systems.
Parallel performance and editorial work is preserved and verified in the same
release gates.

The starting snapshot passed 620 unit/integration tests, lint, production build
and all 11 published-route checks. The shell's default Node 22.12 was below
`package.json`'s engine requirement and failed to start Vitest workers. Validation
uses the already-installed supported Node 24.22.1; no dependency reinstall or
manifest upgrade was needed.

This is not a claim that every possible input, device, hosting configuration or
future defect has been tested. Measured local correctness is distinct from live
service delivery, search indexing and real-user performance.

## Verified improvements

### One publishing contract

[`frontmatter.js`](../src/utils/frontmatter.js) is the sole flat frontmatter
parser, retaining string values. [`postContent.js`](../src/utils/postContent.js)
validates its output for both the lazy full-article loader and
[`seo.mjs`](../scripts/lib/seo.mjs). The metadata-only
[`blogLoader.js`](../src/utils/blogLoader.js) consumes a virtual index generated
by the same validated build reader; listings do not eagerly bundle bodies.

- Required title, slug, summary, publication date and read time must have the
  documented types and non-empty values.
- Category remains optional; when present it must be text.
- Slugs must be URL-safe, at most 120 characters and match the filename.
  Separate files cannot silently publish the same path.
- Dates must be real calendar dates; reading duration must be a positive
  whole-number count of minutes. Article bodies cannot be empty.
- CRLF is normalized, delimiters occupy their own lines and only paired quotes
  are removed.
- Invalid posts fail explicitly instead of quietly disappearing from the
  browser archive.
- A parity test compares every actual authored article between the build and
  browser readers.

The schema and authoring workflow are in [data.md](data.md).

### Literal, accurate metadata

The extracted [`pageShell.mjs`](../scripts/lib/pageShell.mjs) uses replacement
callbacks rather than replacement strings. Authored `$1`, `$&`, dollar/backtick
and dollar/apostrophe sequences are preserved rather than being interpreted by
`String.replace`. Tests cover title, meta, canonical and inline JSON-LD output,
including escaped HTML and closing script tags.

The static homepage is now generated from the same title/description constants
as runtime metadata. Archive/shelf social-image alt text follows the page title.
No new expertise, awards, reviews, organizations or other identity claims have
been invented.

### Honest substantive revisions

Optional `updated` frontmatter records an actual substantive revision on or
after publication. It updates:

- visible runtime and static article bylines;
- article and archive JSON-LD modification dates;
- Open Graph `article:modified_time`;
- article sitemap `lastmod`, plus home/archive dates based on the latest change;
- RSS channel `lastBuildDate`.

Original publication dates, RSS item dates, stable GUIDs and archive ordering
remain unchanged. Rebuilding does not simulate freshness. Existing articles
receive no invented revision dates.

### Working deep links

[`articleHeadings.js`](../src/utils/articleHeadings.js) checks every generated
heading ID against all prior IDs. Repeated "Notes" headings followed by "Notes 1"
can no longer generate two `notes-1` anchors. Runtime rendering and static
Markdown use the same algorithm. Existing non-colliding anchors are preserved.

The build verifier additionally rejects duplicate IDs, broken cross-page
fragment targets, malformed sitemap XML, and article title/description/date/schema
output that differs from authored source.

### Useful archive search, without SEO spam

The archive has local full-text search and an exact-topic filter. Each query word
must match title, summary, category, tags or article text, case- and
accent-insensitively. Matching is literal rather than regex-based. Filtering
preserves publication order and year grouping.

Labels, result announcements, empty-state recovery and focus-restoring Clear
support keyboard and screen-reader use. No search terms are stored or sent to
a search backend. Search creates no crawlable parameter variants, fabricated
keyword pages or `SearchAction` claiming a nonexistent endpoint.

The complete archive remains available without JavaScript. Runtime canonical
and structured data continue to describe the full archive.

Text queries dynamically load the existing full-article module; topic-only
filtering and initial archive visits do not download bodies. Pending searches
announce loading rather than partial matches. Import failures log their cause
and offer visible reload and clear-to-browse recovery. Clearing or leaving the
page ignores late results. Tests exercise body-only matching and these failure
and cancellation boundaries.

### Less unrelated work on reading routes

The homepage is a lazy route, so article and shelf visits do not download all
homepage sections. A direct lower-section link does not fetch three.js until
the hero enters the viewport. Production request assertions verify both
properties, alongside cold cross-route section focus.

Magnetic interactions update motion values instead of React state, and
navigation coalesces scroll-spy measurements into a single animation frame.
Unit tests check render counts, measurement batching and cleanup. The sculpture,
intro, rocket and saved motion preferences retain their existing behavior;
field performance still needs real-user measurement.

### More trustworthy regression gates

- The shared motion mock keeps stable component identities, like real
  `motion.*` elements. Parent rerenders must not artificially remount children,
  reset form state or lose focus.
- Build-helper tests use Node, constructing explicit JSDOM instances only where
  HTML/XML parsing is needed, instead of creating an unused browser environment
  for every helper file.
- Coverage includes frontend and build helpers, with release floors of 95%
  statements, 90% branches, 95% functions and 95% lines. Full coverage runs in CI
  and `npm run check`.
- Archive browser tests cover desktop/mobile filtering, keyboard behavior,
  no-results recovery, axe checks, navigation and no-JavaScript discovery.

The existing suite continues to cover contact failures/cancellation, view
deduplication, dashboard authentication/races, PGlite SQL authorization,
analytics privacy, responsive layout, WebGL, rocket interaction and deployment
output. See [testing.md](testing.md) for coverage boundaries and commands.

## Verification commands

Use a Node version satisfying `package.json`, then:

```bash
npm run check
```

This runs the dependency audit, lint, coverage with thresholds, production build,
generated-output verifier and full desktop/mobile Playwright suite. It blocks a
release rather than treating a passing subset as full validation.

The integrated unit/integration run passes 827 tests across 90 files, with 96.94%
statements, 93.67% branches, 97.62% functions and 97.63% lines. Build helpers
are included, and all four release floors pass. Route-composition tests use
CSSOM stylesheet injection to avoid jsdom reparsing the entire growing
stylesheet on every insertion; real browser tests still verify CSS and layout.
Eight archive/article browser checks pass across desktop and mobile.
A separate 320px browser inspection confirmed working combined text/topic
filtering, unchanged canonical URL and no horizontal overflow.

## Backend, database and hosting boundaries

No new general backend, CMS, schema migration or live database mutation is
necessary for these features. Formspree remains the contact delivery boundary;
Supabase supplies optional view counts and private reporting. SQL behavior is
tested in isolated PGlite, not against production credentials.

The existing safeguards remain: verified database TLS, RLS/grant checks,
owner-UID authorization for aggregate analytics, privacy opt-outs, sanitized
analytics URLs and configuration validation. UI email gating is not treated as
server authorization. Public metrics remain forgeable and are not billing-grade
or bot-resistant counters.

GitHub Pages is static hosting; application tests cannot establish deployed
grants, OAuth configuration, email delivery, abuse quotas, retention policy or
header-level controls unavailable to this host. Those are operational
responsibilities, not silently completed migrations.

## Search operations and potential work

Technical SEO makes accurate authored content discoverable; it cannot guarantee
first place for arbitrary searches. No ranking improvement is claimed without
Search Console and field evidence.

1. Verify the owner's Search Console property, submit the sitemap index and
   inspect representative indexed/canonical URLs.
2. Measure field Core Web Vitals and query impressions/click-through before
   making further performance claims.
3. Publish original, reviewed articles and evidenced project case studies.
4. Define retention and ingestion quotas before introducing an analytics
   ingestion service or scheduled deletion.
5. Add a database published-slug allowlist only with a tested publish/sync
   operation; do not make current optional counts depend on an undeployed table.
6. Perform manual assistive-technology and real OAuth/contact-delivery checks.

[FEATURES.md](../FEATURES.md) separates shipped features, proposed work and
deliberate non-goals. [seo.md](seo.md), [architecture.md](architecture.md) and
[deployment.md](deployment.md) remain the implementation and operations references.
